## Performance analysis

### Summary

Marcus is the Todoist-first persona: Todoist is connected, Google Calendar is disconnected, and Google Calendar should only be selected on explicit mentions such as `google calendar`, `google cal`, or `gcal`. Against that routing policy, the pre-orchestrator router performs well overall.

- Raw domain decisions: 20/21 exact-match by persona policy (95.2%).
- Post-guardrail decisions: 19/21 exact-match by persona policy (90.5%).
- Required-domain recall: 21/21; every query that needed an available routed domain included one.
- Main regression source: guardrails changed an unsupported-domain Notion query from `[]` to `["todoist"]`.
- Latency: average 975 ms, median 959 ms, p95 1149 ms, min 719 ms, max 1209 ms.

### Expected behavior for this persona

- Todoist should receive all task, project, reminder, generic schedule, free/busy, calendar, meeting, and availability requests unless Google Calendar is explicitly named.
- Google Calendar should be routed only when explicitly named, even though it is disconnected, so the orchestrator can explain the unavailable integration.
- Unsupported providers such as Notion or email should return no routed domains.
- Greetings, retractions, and meta/no-op messages should return no routed domains.

### Findings

1. Query 9 over-routes explicit Google Calendar lookup.
   - Query: `check my google cal for thursday plz`
   - Router output: `["google_calendar", "todoist"]`
   - Expected: `["google_calendar"]`
   - Impact: The router correctly detects the explicit Google Calendar request, but adds Todoist unnecessarily. This may cause extra tool planning or mixed-provider answers when the user specifically asked for Google Calendar.

2. Query 15 guardrails create a false positive Todoist route.
   - Query: `check my notion page for meeting notes from yesterday`
   - Raw router output: `[]`
   - After guardrails: `["todoist"]`
   - Expected: `[]`
   - Impact: The raw router handles the unsupported Notion request correctly, but the guardrail layer forces Todoist because the query contains meeting/date language. This is the highest-risk behavior in this eval because it sends an unrelated request to an unrelated connected provider.

3. Generic calendar fallback is consistent.
   - Queries 2, 3, 4, 11, 12, 13, 20, and 21 all route to Todoist as intended for Marcus.
   - This confirms that the explicit-only Google Calendar policy is mostly working: generic terms such as `free`, `schedule`, `cal`, `meetings`, and `booked` do not trigger Google Calendar.

4. Unsupported and no-op raw classifications are good.
   - Query 17 (`email`) returns `[]`.
   - Query 8 (`hey u there`) returns `[]`.
   - Query 19 (`lol nvm forget what i just said`) returns `[]`.
   - The raw router is not over-eager on clearly unsupported or conversational input.

5. Rewrites are mostly helpful but not required for routing quality.
   - Useful rewrites appear on task/project and ambiguous schedule edits, such as queries 1, 3, 6, 13, 14, and 21.
   - Some clear inputs are rewritten anyway, but the rewrites do not appear to degrade the domain decision.

### Latency notes

All 21 requests completed between 719 ms and 1209 ms. The distribution is tight enough for a pre-orchestrator router, with no large outliers:

- Fastest: Query 15 at 719 ms.
- Slowest: Query 13 at 1209 ms.
- Median: 959 ms.
- p95: 1149 ms.

The slowest cases are not tied to failures; Query 13 is correct despite being the max-latency case. The incorrect cases are around the same latency band as the rest of the run, so this eval does not suggest a performance-vs-accuracy tradeoff.

### Recommendations

1. Adjust the guardrail fallback so unsupported named providers do not get coerced into Todoist merely because they contain schedule-like words.
   - For example, `notion`, `email`, `gmail`, `slack`, and other explicit unsupported providers should preserve `domains: []` unless a supported provider is also explicitly requested.

2. Tighten explicit Google Calendar handling.
   - When `google cal`, `gcal`, `google calendar`, or `google_calendar` appears, prefer `["google_calendar"]` unless the query separately asks for tasks or Todoist.
   - Query 12 is a useful contrast: `tasks and meetings both` should stay Todoist-only for Marcus because Google Calendar is not explicitly named.

3. Keep the Marcus prompt's generic-calendar fallback rules.
   - The model follows those rules well and avoids routing generic `calendar`, `schedule`, `free`, `busy`, and `cal` language to disconnected Google Calendar.

### Verdict

The Marcus pre-orchestrator router is ready for the Todoist-first calendar-fallback policy, with one router-level precision issue and one guardrail-level false positive to fix. The raw router is high-recall and mostly high-precision; the guardrail layer is currently the larger correctness risk for this persona.
