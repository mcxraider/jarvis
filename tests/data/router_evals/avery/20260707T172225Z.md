## Performance analysis

This run evaluates the pre-orchestrator router for Avery with Todoist as the task provider, Todoist as the default event provider, and both `todoist` and `google_calendar` connected. The prompt intentionally biases generic schedule, availability, and calendar-like language toward `todoist`, while explicit Google Calendar mentions should route to `google_calendar`.

### Summary

- Queries evaluated: 21
- Raw router decisions matching the prompt contract: 21 / 21
- Final decisions after guardrails matching the prompt contract: 20 / 21
- Raw unsupported-domain handling: 2 / 2 correct (`notion`, `email` returned no domains)
- Guardrail regressions: 1 / 21
- Multi-domain detections: 2 / 2 correct
- Empty-domain detections for conversational or unsupported requests before guardrails: 4 / 4 correct

The raw model router performed well against the current prompt contract. It consistently routed Todoist task/project/reminder requests to `todoist`, explicit Google Calendar requests to `google_calendar`, and mixed task-plus-calendar requests to both domains. The one material problem in the final output is not the raw model decision: Query 15 was correctly classified as unsupported by the raw router, then changed by guardrails from `[]` to `["todoist"]`.

### Latency

- Minimum: 670 ms
- Median: 1008 ms
- Average: 1015 ms
- p95: 1271 ms
- Maximum: 1422 ms
- Under 1000 ms: 9 / 21
- At or above 1000 ms: 12 / 21

Latency is usable but not especially "fast" for a pre-orchestrator router. More than half the requests took at least one second, and the slowest cases were simple routing decisions rather than semantically hard ones. If this router runs on every user turn before orchestration, the current model/prompt combination will be noticeable in interactive use.

### Findings

1. **Guardrails introduce a false positive for unsupported domains.**
   - Query 15: `check my notion page for meeting notes from yesterday`
   - Raw response: `[]`
   - After guardrails: `["todoist"]`
   - Expected by prompt contract: `[]`
   - Impact: the assistant would invoke Todoist for a Notion request, which is both irrelevant and likely to produce a confusing user experience. This is the main correctness issue in the run.

2. **The raw router handles explicit provider selection correctly.**
   - Query 9 routes `check my google cal for thursday plz` to `google_calendar`.
   - Query 10 routes `is there anything on gcal for me tmr morning` to `google_calendar`.
   - Query 14 routes `dont add this to my calendar just keep it on my todo list` to `todoist`.
   - This shows the model respects explicit provider intent and negative provider constraints, even when the utterance is casual or abbreviated.

3. **The prompt's Todoist-as-calendar policy is being followed consistently.**
   - Query 2 `when am i free next week?` routes to `todoist`.
   - Query 3 `Go through my schedule...` routes to `todoist`.
   - Query 4 `put in my cal` routes to `todoist`.
   - Query 11 `block off 2hrs friday afternoon for deep work` routes to `todoist`.
   - Query 21 `which one should zac and i grab dinner` routes to `todoist`.
   - These may look counterintuitive if the desired product behavior is to use Google Calendar for availability and event creation, but they are correct under the current prompt rules.

4. **Multi-domain requests are detected when the user explicitly asks for both task and calendar context.**
   - Query 12 routes `tasks and meetings both` to `["todoist", "google_calendar"]`.
   - Query 20 routes `todos` plus `booked on my cal` to `["todoist", "google_calendar"]`.
   - This is a strong behavior: the router does not over-apply the generic schedule-to-Todoist rule when the user clearly names both work surfaces.

5. **Query rewriting is generally helpful, but one rewrite drops useful nuance.**
   - Query 6: `remind me to text mom back later today`
   - Rewrite: `remind me to text mom back today`
   - The route is correct, but the rewrite weakens the temporal phrase from `later today` to `today`. If downstream tools consume the rewrite, this could affect reminder timing.

6. **Reasoning strings sometimes exceed the requested ten-word limit.**
   - Query 14 uses `calendar rejection, task kept on todoist`, which is short enough semantically but bumps against the instruction style.
   - This has low operational impact because the structured domains are valid, but it shows the model is treating the reasoning limit as soft.

### Recommendations

1. Fix the guardrail fallback so unsupported or empty-domain raw decisions remain empty unless there is a specific, evidence-backed reason to add a domain.
2. Add an assertion to the eval harness that records both raw and post-guardrail correctness, because this run shows raw model accuracy can be masked by guardrail behavior.
3. Consider a cheaper or shorter prompt path for obvious single-domain cases if the pre-orchestrator latency budget is below one second.
4. Preserve temporal modifiers during rewrites, especially phrases such as `later today`, `this morning`, `after lunch`, and `before my flight`.
5. If the desired real-world behavior is to use Google Calendar for generic availability and event blocking, revise rules 2 and 3. The current router is following the written contract, but that contract intentionally sends generic schedule requests to Todoist.
