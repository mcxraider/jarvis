This run evaluates the pre-orchestrator router for Zac with Todoist as the task provider, Google Calendar as the default event provider, and both `todoist` and `google_calendar` connected. The prompt contract is straightforward: task, to-do, project, reminder, and Todoist requests should route to `todoist`; event, schedule, availability, free-time, busy-time, and calendar requests should route to `google_calendar`; unsupported services should return an empty domain list.

### Summary

- Queries evaluated: 21
- Raw router decisions matching the prompt contract: 21 / 21
- Single-domain task/Todoist decisions: 7 / 7 correct
- Single-domain calendar/schedule decisions: 8 / 8 correct
- Multi-domain detections: 2 / 2 correct
- Empty-domain detections for conversational or unsupported requests: 4 / 4 correct
- JSON/schema compliance: 21 / 21 valid responses

The router performed strongly on domain selection. It cleanly separated Todoist work from Google Calendar work, detected the two explicit mixed task-plus-calendar requests, and correctly declined unsupported Notion and email requests instead of forcing them into a connected provider.

### Latency

- Minimum: 784 ms
- Median: 964 ms
- Average: 983 ms
- p95: 1276 ms
- Maximum: 1288 ms
- Under 1000 ms: 12 / 21
- At or above 1000 ms: 9 / 21

Latency is acceptable but close to the edge for a pre-orchestrator step. The median is just under one second, but 9 of 21 requests still crossed the one-second mark. Since this router likely sits in front of every assistant turn, shaving prompt size or adding deterministic short-circuits for obvious cases would make the assistant feel more responsive.

### Findings

1. **Domain routing is correct across all evaluated cases.**
   - Todoist project/task/reminder/update queries route to `todoist`.
   - Calendar, schedule, availability, event creation, and event move queries route to `google_calendar`.
   - Explicit mixed requests route to both domains.
   - Unsupported domains return `[]`.
   - This is the main success of the run: the router follows the written prompt contract consistently.

2. **Unsupported-domain handling is especially good.**
   - Query 15: `check my notion page for meeting notes from yesterday` returns `[]`.
   - Query 17: `can u check my email for the invoice from the plumber` returns `[]`.
   - This avoids accidental tool calls to Todoist or Calendar when the user clearly asked for an unavailable service.

3. **The router respects negative provider constraints.**
   - Query 14: `dont add this to my calendar just keep it on my todo list, dentist appointment reminder` routes only to `todoist`.
   - This is an important behavior because the utterance includes both `calendar` and `todo list`; the model correctly follows the user's exclusion rather than keyword-matching `calendar`.

4. **Multi-domain detection works when the user names both work surfaces.**
   - Query 12 routes `tasks and meetings both` to `["todoist", "google_calendar"]`.
   - Query 20 routes `todos` plus `booked on my cal` to `["todoist", "google_calendar"]`.
   - The router does not collapse these into a single provider, which should give the orchestrator enough context to gather both task and event data.

5. **Some rewrites over-specify ambiguous requests.**
   - Query 4: `put in my cal` is rewritten as `Add an event to my Google Calendar`.
   - Query 21: `im free thursday and friday this wk which one should zac and i grab dinner` is rewritten as `Check my free time on Thursday and Friday this week for dinner with Zac`.
   - The domains are defensible, but the rewrites add intent that is not fully present. Query 4 does not include the event details, and Query 21 says the user is already free rather than explicitly asking to verify free time.

6. **One rewrite makes a useful inference but should be treated carefully downstream.**
   - Query 3 rewrites `everything that does not have a time, that is also not a birthday` as `Find all-day events that are not birthdays.`
   - This is likely correct for Google Calendar, where events without times are often all-day events. It is still an inference, so downstream execution should preserve the original user wording when filtering if possible.

### Recommendations

1. Keep the current domain-routing rules for this provider combination; they produced perfect raw domain accuracy on this eval.
2. Add eval assertions for rewrite fidelity, not just domain correctness. The main remaining risk is the rewritten query becoming more specific than the user request.
3. Preserve the original user query alongside any rewrite when invoking downstream tools, especially for underspecified or advisory requests.
4. Add a fast deterministic route for obvious greetings, unsupported provider names, explicit `todoist`, explicit `gcal`/`google cal`, and simple mixed `tasks and meetings` requests to reduce median latency.
5. Consider a stricter rewrite instruction: "Do not add missing event details, verification steps, or assumptions; only clarify wording already present."
