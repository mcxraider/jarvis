### Findings

1. **Domain routing is correct across the full eval.** All 21 raw decisions match the written Phoebe policy. The router correctly ignores connection status for clear Todoist requests, which is important because Todoist is disconnected but still semantically required for queries 1, 5, 6, 7, 14, 16, and 18.

2. **Google Calendar is selected consistently for Phoebe's default event surface.** Generic availability and schedule requests route to `google_calendar`, including Query 2 (`when am i free next week?`), Query 3 (`Go through my schedule...`), Query 4 (`put in my cal`), Query 11 (`block off 2hrs friday afternoon`), Query 13 (`move my dentist thing`), and Query 21 (`which one should zac and i grab dinner`). This is the expected contrast with Todoist-first personas.

3. **Unsupported providers are handled cleanly.** Query 15 (`notion`) and Query 17 (`email`) both return `[]`. The router does not get distracted by adjacent words such as `meeting notes`, `yesterday`, or `invoice`, which could otherwise cause false positive routing to Calendar or Todoist.

4. **Multi-domain requests are detected when the user asks for both work surfaces.** Query 12 (`tasks and meetings both`) and Query 20 (`todos` plus `booked on my cal`) both route to `["todoist", "google_calendar"]`. This is the right behavior even though Todoist is disconnected, because the user's requested answer depends on both task and calendar context.

5. **The main quality risk is downstream ambiguity, not router selection.** Query 4 (`put in my cal`) correctly routes to Google Calendar, but the request lacks event details. Query 21 correctly routes to Google Calendar, but the user claims they are already free and asks for a recommendation; the calendar lookup may still be useful, but the orchestrator should be ready to answer conversationally or ask for preferences if no event data is needed.

6. **Rewrites are mostly helpful but occasionally over-specific.** Query 21 is rewritten as `Check my availability on Thursday and Friday of this week for dinner plans with Zac`, which changes a recommendation request into a pure availability check. The domain route is still right, but if the orchestrator relies heavily on `rewritten_query`, it may under-answer the user's actual "which one should we choose" intent.

7. **Latency is acceptable and tighter than sibling Todoist-first runs.** Sixteen of 21 decisions completed under one second, with a median of 880 ms and a max of 1238 ms. The slowest case, Query 10 at 1238 ms, was a straightforward explicit `gcal` lookup and still routed correctly, so this run does not show an accuracy/latency tradeoff.

### Recommendations

1. Keep the Phoebe routing prompt as-is for domain selection. It cleanly separates Todoist work from Google Calendar work and handles disconnected Todoist correctly.
2. Add eval assertions for rewrite preservation, especially when a user asks for a recommendation or decision rather than only a lookup.
3. Preserve the empty-domain behavior for explicit unsupported providers. This run shows the raw router can do that reliably, and downstream guardrails should avoid coercing these cases into supported domains.
4. Consider tracking "needs clarification" separately from domain routing for underspecified creation requests such as `put in my cal`.

### Verdict

Phoebe's pre-orchestrator router is ready from a domain-routing perspective. The run shows perfect raw policy match, good unsupported-provider precision, correct multi-domain recall, and sub-second median latency. The next improvements should focus on rewrite fidelity and downstream clarification handling rather than changing the domain classifier.
