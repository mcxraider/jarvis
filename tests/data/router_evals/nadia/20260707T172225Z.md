## Performance analysis

This run evaluates the pre-orchestrator router for Nadia with Todoist as the task provider, Google Calendar as the event provider, and both `todoist` and `google_calendar` connected. Under this prompt, task and project requests should route to `todoist`; schedules, events, availability, free-time, busy-time, and calendar edits should route to `google_calendar`; conversational or unsupported-domain turns should return no domains.

### Summary

- Queries evaluated: 21
- Raw router decisions matching the prompt contract: 20 / 21
- Clear false negatives: 1 / 21
- Unsupported-domain handling: 2 / 2 correct (`notion`, `email` returned no domains)
- Conversational/no-op handling: 2 / 2 correct (`hey u there`, `lol nvm forget what i just said`)
- Multi-domain detections: 2 / 2 correct
- JSON/schema compliance: 21 / 21

The router is broadly reliable for Nadia's connected-provider setup. It correctly separates Todoist task/project/priority requests from Google Calendar schedule, availability, event creation, and event rescheduling requests. It also handles explicit multi-domain requests and unsupported tools without over-routing. The one material miss is Query 6: a reminder request that should route to Todoist instead returned an empty domain list.

### Latency

- Minimum: 772 ms
- Median: 1038 ms
- Average: 993 ms
- p95: 1131 ms
- Maximum: 1243 ms
- Under 1000 ms: 10 / 21
- At or above 1000 ms: 11 / 21

Latency is acceptable but still heavy for a pre-orchestrator decision that runs before the real assistant work begins. The median request is just over one second, and more than half the run crosses the one-second mark. The slowest result, Query 13 at 1243 ms, is an ordinary event-reschedule classification rather than a uniquely difficult case, so the cost appears to be mostly model/prompt overhead.

### Findings

1. **Reminder language is under-routed.**
   - Query 6: `remind me to text mom back later today`
   - Raw response: `[]`
   - Expected by prompt contract: `["todoist"]`
   - Impact: the assistant would skip Todoist for a normal reminder/task creation request. This is the main correctness issue in the run and likely needs either a prompt rule that explicitly names reminders or a deterministic keyword fallback for `remind me`.

2. **Calendar routing is strong for generic and explicit calendar intent.**
   - Query 2 routes `when am i free next week?` to `google_calendar`.
   - Query 3 routes schedule inspection with filtering to `google_calendar`.
   - Query 4 routes abbreviated `put in my cal` to `google_calendar`.
   - Query 11 routes blocking time for deep work to `google_calendar`.
   - Query 13 routes moving a dentist appointment to `google_calendar`.
   - This is the desired behavior for Nadia because Google Calendar is her configured event provider.

3. **Todoist routing is strong when the user says tasks, projects, todo list, or Todoist.**
   - Query 1 routes Todoist project discovery to `todoist`.
   - Query 5 routes today's urgent tasks to `todoist`.
   - Query 7 routes adding an item to a grocery project to `todoist`.
   - Query 14 respects the negative calendar instruction and routes the reminder to `todoist`.
   - Query 16 and Query 18 correctly route overdue-task lookup and priority editing to `todoist`.

4. **Multi-domain requests are detected cleanly.**
   - Query 12 routes `tasks and meetings both` to `["todoist", "google_calendar"]`.
   - Query 20 routes `todos` plus `booked on my cal` to `["todoist", "google_calendar"]`.
   - These cases show the router can widen the tool surface when the user explicitly asks for both work streams.

5. **Unsupported domains stay empty instead of falling back to a connected provider.**
   - Query 15: `check my notion page for meeting notes from yesterday` returns `[]`.
   - Query 17: `can u check my email for the invoice from the plumber` returns `[]`.
   - This is correct for the prompt's two-domain setup and avoids irrelevant Todoist or Calendar calls.

6. **Query rewrites are generally helpful, but they can add downstream specificity.**
   - Query 11 rewrites `block off 2hrs friday afternoon for deep work` to a clear event-creation request.
   - Query 10 expands `gcal` and `tmr morning` into Google Calendar and tomorrow morning.
   - Query 2 rewrites free-time lookup clearly.
   - The rewrites look safe in this run, but reminder rewrites should preserve timing modifiers such as `later today` once Query 6 is fixed.

### Recommendations

1. Add `reminders` explicitly to the Todoist domain description and routing rule, for example: "Route tasks, to-dos, reminders, and projects to `todoist`."
2. Add a regression fixture for `remind me to ...` phrasing, including variants with `later today`, `tomorrow`, and `next week`.
3. Keep the explicit provider and negative-provider examples because Query 14 shows they help preserve user intent.
4. If the pre-orchestrator budget is below one second, test a shorter prompt or deterministic fast path for obvious single-domain phrases such as `tasks`, `todoist`, `gcal`, `calendar`, `free`, and `schedule`.
5. Continue tracking unsupported-domain cases separately from empty conversational turns; both are correct empties, but they fail differently if future guardrails over-route them.
