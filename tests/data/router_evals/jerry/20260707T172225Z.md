## Analysis

### Summary

Jerry's routing profile is intentionally Todoist-heavy:

- `task_provider`: `todoist`
- `event_provider`: `todoist`
- `calendar_usage`: `explicit_only`
- Active providers: `todoist`, `google_calendar`

Under that policy, generic schedule, free/busy, calendar, meeting, and appointment language should usually route to `todoist`; `google_calendar` should only appear when the user explicitly says `google calendar`, `google cal`, `gcal`, or `google_calendar`.

The router mostly follows that contract. The raw model routed correctly on 19 of 21 queries by the written policy. The post-router guardrails fixed both raw over-routes to Google Calendar, but introduced one clear false positive for an unsupported Notion request. Final guardrailed routing is therefore 20 of 21 by the same policy.

### Findings

1. **The base router respects Jerry's explicit-only Google Calendar preference.** Queries 2, 3, 4, 11, 20, and 21 all contain generic availability, schedule, calendar, meeting, or free-time language, and the raw router keeps them on `todoist`. That matches Jerry's preference that Todoist handles generic scheduling.

2. **Explicit Google Calendar mentions are handled cleanly.** Query 9 (`google cal`) and Query 10 (`gcal`) both route only to `google_calendar`, which is the expected behavior for this persona.

3. **The model sometimes over-includes Google Calendar on mixed task/event phrasing.** Query 12 (`tasks and meetings both`) and Query 13 (`dentist thing ... same time`) both raw-route to `["todoist", "google_calendar"]` even though Google Calendar was not explicitly requested. The guardrail correctly removes `google_calendar` in both cases.

4. **The guardrail has a false-positive fallback for unsupported domains.** Query 15 (`check my notion page for meeting notes from yesterday`) raw-routes to `[]`, which is correct because Notion is not available in this eval. The guardrail then sees `meeting` and rewrites the final decision to `["todoist"]`. That exposes Todoist tools for an unsupported Notion lookup and is the clearest final-routing bug in this run.

5. **Reasoning frequently violates the requested 10-word limit.** Examples include Query 2, Query 13, and Query 21. This does not break tool selection, but it means the router is not strictly following the output schema guidance.

6. **Query rewriting is useful but inconsistent.** Rewrites are helpful for Query 1, Query 5, Query 12, Query 13, and Query 20. Several equally ambiguous natural-language requests, such as Query 4 (`put in my cal`) and Query 21, receive no rewrite. That is acceptable for routing, but less helpful if the orchestrator later relies on `rewritten_query` to clarify execution intent.

### Recommendations

1. **Fix the guardrail fallback so unsupported-domain requests do not become Todoist requests.** If the raw decision is empty and the query contains an unsupported domain noun such as `notion`, `email`, `gmail`, `slack`, or `docs`, keep the domains empty instead of applying the generic event fallback.

2. **Make the generic-event fallback more conditional.** The current pattern treats words like `meeting` as enough to add the event provider when the raw domains are empty. That is useful for pure schedule questions, but unsafe when the sentence is anchored to another service.

3. **Add eval assertions for raw and final decisions separately.** This run shows why both matter: raw had two model mistakes that final routing corrected, while final routing had one guardrail-created mistake that raw routing avoided.

4. **Tighten schema compliance checks around `reasoning`.** The router should either enforce the 10-word reasoning limit after parsing or tests should stop asking for it if the field is only diagnostic.

5. **Consider recording expected domains in `router_queries.py`.** The current report requires manual policy interpretation. Adding expected raw/final domains per persona or per query would turn this from a transcript into a repeatable regression suite.
