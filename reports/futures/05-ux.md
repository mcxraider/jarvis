# User Experience

User-facing features and polish. These depend on the foundation, safety, and reliability layers being solid first.

---

## 5.1 Telegram Conversation Gating and HITL Routing

**Status:** No active-run tracking. A mid-run Telegram message from the user can accidentally start a second graph thread.

**Required state machine per chat:**
`idle` → `running` → `waiting_for_clarification` | `waiting_for_confirmation` → `completed` | `failed`

Only `idle` can start a new run. Only waiting states can resume one.

**Key behaviors:**
- Reject or ignore new user messages while the graph is actively running.
- Accept user messages during a run only when the graph is explicitly waiting for HITL input.
- Treat accepted HITL messages as replies to the existing paused graph, not new conversation starts.
- Expire stale waiting states so an old clarification prompt cannot capture unrelated future messages.
- `/cancel` or `[Cancel request]` cancels the active graph or waiting clarification, clears the lock, and returns a deterministic cancellation response.
- `/status` returns current run state — both commands bypass the active-run lock.

**HITL message correlation:**
- Use Telegram force-reply markup for clarification/confirmation prompts.
- Store the Telegram message ID for each HITL prompt; accept replies only when `reply_to_message.message_id` matches the latest pending prompt.
- "Last-prompt wins": if the graph asks a new HITL question, invalidate earlier pending prompt IDs.
- Resuming a paused graph from a HITL answer must be idempotent (duplicate Telegram deliveries do not resume twice).

## 5.2 Clarification Memory and Confirmation Thresholds

**Status:** Answering a clarification question starts a new conversation instead of resuming the paused graph.

**Fix — clarification memory:**
- Store pending clarification state: original plan, missing fields, expiry.
- Short follow-up replies resume the original orchestration thread.
- Expire stale clarification state after a configurable number of turns or minutes.
- Do not mutate if the follow-up appears unrelated to the pending clarification.

**Confirmation thresholds:**
Require user confirmation before executing plans that:
- Delete more than one task.
- Complete or create more than a configured threshold of tasks.
- Reschedule many tasks at once.
- Touch multiple external systems.

The confirmation message should summarize all intended side effects before anything mutates.

## 5.3 Stateful Progress Messages

**Status:** Long-running agentic flows are silent from the user's perspective.

**Appropriate progress updates (safe, no internal reasoning exposed):**
- "Understanding the request."
- "Checking recent context."
- "Planning the Todoist changes."
- "Confirming the target task."
- "Creating tasks in Todoist."
- "Retrying after a temporary provider issue."
- "Preparing the final summary."

**Behavior:**
- Send or edit a single Telegram message as the graph moves through major nodes.
- Throttle updates; avoid noisy sends for fast requests.
- Never reveal prompts, model reasoning, raw tool payloads, or sensitive data.
- On failure, replace the progress message with a concise final error.

## 5.4 Natural-Language Task Lookup (Before Edit / Delete)

**Status:** Edit, complete, and delete work best only when the task ID is already known. Users say "mark buy groceries as done."

**Fix — lookup-before-mutate flow:**
1. Search Todoist for likely matching tasks using the user's natural language.
2. Rank matches by relevance.
3. One confident match → execute the mutation.
4. Multiple matches → ask the user to choose from a numbered list.
5. No match → explain that no matching task was found.
6. Report result deterministically.

## 5.5 Bulk Task Operations

**Status:** No support for batch changes across existing tasks.

**Examples:**
- "Move all overdue admin tasks to tomorrow."
- "Complete all tasks with the 'waiting' label."
- "Reschedule this week's low-priority tasks to next week."

**Behavior:**
- Search for affected tasks first.
- Preview affected count when the action is broad or risky.
- Ask for confirmation before destructive or large updates.
- Execute compatible independent updates through the batch executor.
- Return a clear success/failure/skipped report.

## 5.6 Recurring Task Support

**Status:** Natural-language recurring tasks (e.g., "every Tuesday at 9am") are parsed by the model with no verification.

**Fix:**
- Parse recurrence carefully and preview the interpreted schedule when the expression is ambiguous.
- Ask for confirmation before creating the recurring item.
- The return-to-user node must avoid claiming recurrence behavior it cannot verify — say only what Todoist accepted.

---

## 5.7 Daily Planning and Task Decomposition

Let Jarvis help the user plan work, not only mutate tasks.

**Expected behavior:**
- Fetch overdue, today, and upcoming tasks.
- Group by urgency, priority, label, or project.
- Identify overload (too many tasks due on one day).
- Suggest a realistic daily plan.
- Decompose broad goals into actionable subtasks.
- Optionally create or reschedule tasks after user confirmation.

---

## 5.8 Interrupt Timeouts and Graceful Turn-Limit Handling

**Status:** A paused HITL thread waits forever. Hitting `MAX_AGENT_TURNS` returns a bare error string.

**Fix:**
- Add a configurable TTL to paused HITL interrupts; auto-expire with a "that prompt expired" response and return to `idle`.
- Before resuming a paused clarification, verify the thread is still valid and has not expired; if it is stale, respond with a deterministic message such as "This request expired because it was waiting for details for too long. Please start again.".
- On turn-limit, force a summarizing partial answer ("completed X and Y, blocked on Z") rather than an opaque error.

---

## 5.9 Streaming

**Status:** Responses are returned in full after the graph completes, adding perceived latency.

**Fix:** Stream tokens to the UI where the transport supports it. This complicates tool-call handling (tokens must pause during tool execution) — implement only after the core loop is stable.
