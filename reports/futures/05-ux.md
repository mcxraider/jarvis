## 5.1 Telegram Conversation Gating and HITL Routing 🟡

**Status (2026-06-24):** Partial. `PendingClarificationStore` exists with TTL expiry, status tracking, and Postgres support. HITL resume via `/resume` endpoint works. **Gap:** No state machine enforcement (idle/running/waiting). No force-reply markup. No active-run lock preventing concurrent messages.

**Original problem:** No active-run tracking. A mid-run Telegram message from the user can accidentally start a second graph thread.

**Required state machine per chat:**
`idle` → `running` → `waiting_for_clarification` | `waiting_for_confirmation` → `completed` | `failed`

Only `idle` can start a new run. Only waiting states can resume one.

**Key behaviors:**
- Reject or ignore new user messages while the graph is actively running.
- Accept user messages during a run only when the graph is explicitly waiting for HITL input.
- Treat accepted HITL messages as replies to the existing paused graph, not new conversation starts.
- Expire stale waiting states so an old clarification prompt cannot capture unrelated future messages.
- `/cancel` or `[Cancel request]` cancels the active graph or waiting clarification, clears the lock, and returns a deterministic cancellation response.
- `/status` returns current run state — both commands bypass the active-run lock.

**HITL message correlation:**
- Use Telegram force-reply markup for clarification/confirmation prompts.
- Store the Telegram message ID for each HITL prompt; accept replies only when `reply_to_message.message_id` matches the latest pending prompt.
- "Last-prompt wins": if the graph asks a new HITL question, invalidate earlier pending prompt IDs.
- Resuming a paused graph from a HITL answer must be idempotent (duplicate Telegram deliveries do not resume twice).

## 5.2 Clarification Memory and Confirmation Thresholds 🟡

**Status (2026-06-24):** Partial. Confirmation gate exists in `confirm.py` with batch summaries. Risk classification in `risk.py` with `CONFIRM_BULK_THRESHOLD` (default 5). **Gap:** Clarification memory (storing pending plan, missing fields, field tracking) not fully implemented. No non-relatedness check for follow-ups.

**Original problem:** Answering a clarification question starts a new conversation instead of resuming the paused graph.

**Fix — clarification memory:**
- Store pending clarification state: original plan, missing fields, expiry.
- Short follow-up replies resume the original orchestration thread.
- Expire stale clarification state after a configurable number of turns or minutes.
- Do not mutate if the follow-up appears unrelated to the pending clarification.

**Confirmation thresholds:**
Require user confirmation before executing plans that:
- Delete more than one task.
- Complete or create more than a configured threshold of tasks.
- Reschedule many tasks at once.
- Touch multiple external systems.

The confirmation message should summarize all intended side effects before anything mutates.

## 5.3 Stateful Progress Messages ✅

**Status (2026-06-24):** Done. `TelegramProgressReporter` in `src/services/telegram/telegram-progress-reporter.ts` now shows event-driven stage-specific labels mapped from `LangGraphProgressEvent.stage`. Labels include "Thinking...", "Planning actions...", "Calling Todoist...", "Checking Todoist...", "Writing response...", etc. 2s debounce prevents rate-limit issues. Heartbeat dot animation (8s) shows liveness. Falls back to timer rotation if no streaming events arrive. Rich mode uses `<tg-thinking>` with custom emoji; plain mode edits a regular message.

**Original problem:** Long-running agentic flows are silent from the user's perspective.

**Appropriate progress updates (safe, no internal reasoning exposed):**
- "Understanding the request."
- "Checking recent context."
- "Planning the Todoist changes."
- "Confirming the target task."
- "Creating tasks in Todoist."
- "Retrying after a temporary provider issue."
- "Preparing the final summary."

**Behavior:**
- Send or edit a single Telegram message as the graph moves through major nodes.
- Throttle updates; avoid noisy sends for fast requests.
- Never reveal prompts, model reasoning, raw tool payloads, or sensitive data.
- On failure, replace the progress message with a concise final error.

## 5.4 Natural-Language Task Lookup (Before Edit / Delete) ❌

**Status (2026-06-24):** Not started. No fuzzy search or lookup-before-mutate flow.

**Original problem:** Edit, complete, and delete work best only when the task ID is already known. Users say "mark buy groceries as done."

**Fix — lookup-before-mutate flow:**
1. Search Todoist for likely matching tasks using the user's natural language.
2. Rank matches by relevance.
3. One confident match → execute the mutation.
4. Multiple matches → ask the user to choose from a numbered list.
5. No match → explain that no matching task was found.
6. Report result deterministically.

## 5.5 Bulk Task Operations ❌

**Status (2026-06-24):** Not started. No bulk operation executor or search → preview → confirm flow.

**Original problem:** No support for batch changes across existing tasks.

**Examples:**
- "Move all overdue admin tasks to tomorrow."
- "Complete all tasks with the 'waiting' label."
- "Reschedule this week's low-priority tasks to next week."

**Behavior:**
- Search for affected tasks first.
- Preview affected count when the action is broad or risky.
- Ask for confirmation before destructive or large updates.
- Execute compatible independent updates through the batch executor.
- Return a clear success/failure/skipped report.

## 5.10 Thinking Indicator for All Non-User-Facing States ❌

**Status (2026-06-25):** Not started. Progress labels exist (5.3) but no persistent `<thinking>` block shown during internal processing.

**Original problem:** The user has no visual cue that the system is actively working unless it is explicitly asking them something or delivering a final response. During internal graph states — tool execution, planning, routing, summarisation, verification — the user sees silence or a generic dot animation, with no indication that the model is mid-thought.

**Rule:** Whenever the graph is in any state that is NOT one of the following user-facing states, a `<thinking>` block (or Telegram equivalent) MUST be visibly shown to the user:
- Asking the user a clarification question
- Asking the user for confirmation
- Delivering the final response

In other words: if the model is not waiting on user input and has not finished responding, the user should always see a thinking/processing indicator.

**States that require the thinking indicator:**
- Agent reasoning / LLM inference
- Tool selection and planning
- Tool execution (Todoist calls, search, etc.)
- Result processing and summarisation
- Verification / hallucination checks
- Routing decisions between nodes
- Retry loops

**Behavior:**
- The `<tg-thinking>` block (or `<blockquote expandable>` fallback) should appear immediately when the graph enters any internal processing state.
- The indicator should persist continuously until the graph transitions to a user-facing output state.
- If the graph moves between multiple internal states (e.g., planning → tool call → summarise), the thinking indicator stays visible throughout — no flicker or gap.
- The indicator is dismissed only when the graph emits a user-facing message (clarification, confirmation, or final answer).
- This is distinct from the stage-specific progress labels in 5.3 — those labels can appear *within* the thinking block to show what stage is active, but the thinking block itself is the envelope that signals "system is working."

**Trade-off:** Minimal — Telegram already supports `<tg-thinking>` blocks and the progress reporter infrastructure exists. This is primarily a state-machine rule: default to showing the indicator, dismiss only on user-facing output.
