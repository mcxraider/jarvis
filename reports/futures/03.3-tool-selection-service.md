# 3.3 Tool Selection Service (Design)

Deep design for roadmap item [§3.3 Tool Selection Layer](03-agent-intelligence.md). This document supersedes the original Todoist-only draft. The headline change: the selector is designed as a **modular, app-agnostic service** so that (a) a **BM25 / semantic retrieval** strategy can be slotted in later without touching the pipeline, and (b) it scales to **more tools and more apps** (calendar, gmail, notion) — not just Todoist.

---

## 1. Context and Goal

**Status.** Every Todoist tool is bound to the orchestrator on every model call. Today that is one place: `agents/agent_api/app/graph/nodes/orchestrator.py:121`:

```python
assistant_message = agent_client.create_message(messages, get_todoist_tools())
```

`get_todoist_tools()` always returns the full schema list (`ask_user` + 7 Todoist tools). This works at the current scale but degrades as the toolset grows:

- **Tool-choice confusion.** For every request the model reasons over all tools even when one or two are relevant. This raises wrong-tool calls, unnecessary lookups, and inconsistent behaviour across similar prompts.
- **Prompt cost.** Every schema is re-sent on every turn of the agent loop.

These problems get worse as new Todoist operations and new apps (calendar, gmail, notion — already scaffolded as empty placeholders under `agents/agent_api/app/tools/`) come online.

**Goal.** Before tools are bound to the model, select a small, relevant subset based on the user query, mutation mode, and deterministic intent matching. The orchestrator should only see tools likely to be useful for the current request.

**Modularity goal (new).** The selection logic must be:

1. **Strategy-pluggable** — deterministic regex/alias matching now; BM25 or embedding-based retrieval later, as a drop-in, with no change to the surrounding pipeline.
2. **App-agnostic** — Todoist is simply the first registered app. Calendar, Gmail, and Notion register the same way.

The selector **does not execute tools**. It only decides which tools are eligible and relevant. Execution stays with `TodoistToolDispatcher` (`agents/agent_api/app/tools/todoist/tools.py`).

## 2. Current State (grounded in the code)

| Concern | Where it lives today | Note for the design |
|---|---|---|
| Bind seam | `graph/nodes/orchestrator.py:121` | The **one** place tools are bound. Selector slots in here. |
| Tool schemas (model contract) | `tools/todoist/schemas.py` → `get_todoist_tools()` | OpenAI/DeepSeek function schemas. `create_message(messages, tools)` expects this `List[Dict]` shape. |
| Executable wrappers | `tools/todoist/tools.py` → `build_todoist_langchain_tools()` | LangChain `@tool` wrappers used by the `ToolNode`. |
| Execution map | `tools/todoist/tools.py:28` → `TodoistToolDispatcher.supported_tools` | name → client method. |
| Mutation flag | `constants.py` → `ALLOW_MUTATIONS`; enforced `tools/todoist/tools.py:100` | Mutations are **already blocked at execution** when off. |
| Mutating tool set | `tools/todoist/schemas.py` → `MUTATING_TOOL_NAMES` | `{add, update, complete, delete}`. |
| HITL pseudo-tool | `schemas.py` → `ASK_USER_TOOL_NAME`; routing via `is_ask_user_tool_call`, `graph/edges.py`, `graph/builder.py` (`hitl` node) | `ask_user` is load-bearing — see §3. |
| Tracing | `tracing.py` → `TracePrinter.event(...)` + LangSmith `@traceable` | Reuse for selection traces. |
| Multi-app scaffolding | empty `tools/calendar/`, `tools/gmail/`, `tools/notion/` `__init__.py` | The repo already anticipates multiple apps. |

**Tool metadata is split across three sources** (`schemas.py`, `tools.py` wrappers, dispatcher map). Any registry we add must reconcile these or it becomes a fourth source that drifts.

**What does not exist yet (and the draft wrongly assumed):** tool health checks, per-integration enabled flags, auth-state tracking, and a permissions/safety policy. Health checks are a *separate* roadmap item ([§3.4](03-agent-intelligence.md)).

## 3. Feasibility Assessment (draft → correction)

| Draft claim / assumption | Status | Correction baked into this design |
|---|---|---|
| Todoist-specific registry & selector | Misaligned with the modularity goal | Generalized to an **app-agnostic Tool Selection Service**; Todoist is the first registered app. |
| Hard filters: tool health, integration-enabled, auth, permissions | **Not implemented** | Modelled as **registry fields with static defaults** (`enabled=True`, `healthy=True`, `requires_auth`), with documented hooks to wire real checks later (cross-ref §3.4). The doc does **not** pretend runtime health/auth checks exist today. |
| Mutation-mode hard filter | Exists, enforced at the dispatcher | Kept as a selector filter, but the **dispatcher remains the enforcement boundary**. Selector-level filtering is prompt hygiene + defense-in-depth, not the safety guarantee. |
| Selector "returns a list of tools" | Underspecified | Two outputs: **(a)** an OpenAI schema `List[Dict]` for binding (matches `create_message`), and **(b)** a structured `SelectionResult` for tracing. |
| `ask_user` not mentioned in selection | **Gap — would break HITL** | New **`always_include`** rule: `ask_user` is bound on every turn regardless of selection or fallback. |
| Three metadata sources unaddressed | Drift risk | Registry is the **single source of truth**; `get_todoist_tools()` (and optionally the dispatcher map) derive from it, preserving the legacy import surface used by `service.py` and `tests/agents/test_jarvis.py`. |
| Behaviour when zero tools survive hard filters | Unspecified | Defined: bind only the `always_include` set (`ask_user`); the model answers or asks. |
| Regex filters described as scattered | Maintainability | Aliases/patterns live **in registry records** and are compiled once. |

Everything in the draft that is *correct and valuable* — the per-prompt routing table, dependency-expansion reasoning, confidence signals, and failure modes — is preserved below, re-homed under the generic structure.

## 4. Target Architecture

Five layers, each app-agnostic:

```text
User query
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Tool Registry        describes every tool across all apps    │
│   (ToolSpec records: intents, aliases, patterns, deps, …)    │
└─────────────────────────────────────────────────────────────┘
   │ candidates (+ metadata)
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Tool Selection Service                                       │
│   a. Hard filters      (registry-driven eligibility)         │
│   b. Match             (MatchStrategy — regex now, BM25 next) │
│   c. Dependency expand  (co-select lookups for mutations)     │
│   d. Confidence gate    (high / medium / low → fallback)      │
│   e. Always-include     (union ask_user)                      │
└─────────────────────────────────────────────────────────────┘
   │ (a) OpenAI schema list  +  (b) SelectionResult
   ▼
┌──────────────────────────┐     ┌──────────────────────────────┐
│ Orchestrator (agent node)│     │ Tracing layer (TracePrinter)  │
│   binds selected schemas │     │   logs why tools were picked  │
└──────────────────────────┘     └──────────────────────────────┘
   │ tool calls
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Dispatcher   validates + executes (enforcement boundary)     │
└─────────────────────────────────────────────────────────────┘
```

Responsibility split:

- **Registry** describes available tools.
- **Selector** decides which tools are relevant.
- **Orchestrator** plans and calls tools (sees only the selected set).
- **Dispatcher** validates and executes — and remains the place mutation mode is *enforced*.
- **Tracing** records why tools were selected or rejected.

This improves system intelligence *indirectly*: the model does not get smarter; it gets more reliable because it sees a smaller, cleaner, more relevant action space.

## 5. Data Models

Illustrative shapes (dataclasses/TypedDicts in the eventual implementation — not prescriptive field-for-field).

### `ToolSpec` — one registry record per tool

```text
name            str          # callable tool name, e.g. "add_todoist_task"
app             str          # "todoist" | "calendar" | "gmail" | "notion"
description     str          # human/LLM facing
intents         list[str]    # e.g. ["task.create"]
aliases         list[str]    # keywords: ["add", "create", "remind me"]
patterns        list[str]    # regexes, compiled once at registration
mutates         bool         # → MUTATING_TOOL_NAMES today
requires_auth   bool         # static default; real check later (§3.4)
enabled         bool = True   # static default; per-integration flag later
healthy         bool = True   # static default; health check later (§3.4)
permissions     list[str]    # placeholder for safety policy
dependencies    list[str]    # tool names to co-select (e.g. ["get_tasks"])
always_include  bool = False  # True only for ask_user
schema          dict         # the OpenAI/DeepSeek function schema
```

The registry derives the bind-time schema list, so `get_todoist_tools()` becomes a thin wrapper over `registry.schemas(app="todoist")` and the legacy import surface keeps working.

### `SelectionContext` — input to the selector

```text
query           str          # latest user request (state["user_prompt"])
allow_mutations bool         # from ALLOW_MUTATIONS
enabled_apps    set[str]     # future; defaults to all registered apps
auth_state      dict         # future; defaults to "assume authed"
registry        ToolRegistry
```

### `SelectionResult` — structured output (for tracing + binding)

```text
selected_schemas    list[dict]   # (a) bound to the model — create_message contract
selected_names      list[str]
detected_intents    list[str]
scores              dict[str, float]
reasons             dict[str, list[str]]   # why each tool was selected
rejected            dict[str, str]          # tool → rejection reason
fallback_used       bool
dependencies_added  list[str]
```

`selected_schemas` is exactly the `List[Dict]` shape `DeepSeekAgentClient.create_message(messages, tools)` already expects, so binding is a drop-in replacement for `get_todoist_tools()`.

## 6. Matching Strategies (the modular core)

Matching is behind a small interface so retrieval methods are interchangeable:

```text
class MatchStrategy:
    def match(self, query: str, candidates: list[ToolSpec]) -> list[MatchResult]: ...

MatchResult = { tool_name: str, score: float, reasons: list[str] }
```

- **v1 — `DeterministicMatcher`.** Alias, regex, and intent-pattern matching read from each `ToolSpec`. No model call. This is the only strategy needed for the current test prompts.
- **Future — `BM25Matcher`.** Lexical retrieval over a tool-description/alias corpus built from the registry. Drops in by implementing the same interface; the pipeline, hard filters, dependency expansion, confidence gate, and tracing are unchanged.
- **Future — `SemanticMatcher`.** Embedding similarity for paraphrased requests.

The selector composes **one or more** strategies (config-driven, e.g. `JARVIS_TOOL_MATCH_STRATEGIES`), and merges their `MatchResult`s by max-score per tool with combined reasons. This makes "deterministic now, BM25/semantic later, or both in a hybrid" a configuration change rather than a rewrite.

Aliases and regexes are centralized in registry records and compiled once at registration — not scattered across the codebase.

## 7. Selection Pipeline

Run in order. Each stage is app-agnostic.

**a. Hard filters (registry-driven).** Remove tools that must never be shown for this request, *before* any matching:

- `enabled` is false (integration off — static default `True` today).
- `healthy` is false (unhealthy/deprecated — static default `True` today; §3.4).
- `requires_auth` and the app is unauthenticated (assume authed today).
- `mutates` and `allow_mutations` is false.
- permission/safety policy blocks it (placeholder today).

This is the most important safety-adjacent layer. (Reminder: mutation mode is *enforced* at the dispatcher; this filter is prompt hygiene + defense-in-depth.) `always_include` tools (`ask_user`) bypass app/intent filtering but still respect nothing that would break HITL.

**b. Match.** Run the active `MatchStrategy`(ies) over the survivors → scored tools and detected intents.

**c. Dependency expansion.** For any selected mutating tool, co-select its `dependencies`. Most natural-language mutations reference a task by description, not ID, so the agent needs a lookup first:

- complete → `get_tasks` + `complete_task`
- update/reschedule/priority → `get_tasks` + `update_todoist_task`
- delete → `get_tasks` + `delete_todoist_task`

This is deterministic and handled by the selector, not left to the model.

**d. Confidence gate.**

- **High** (clear single/multi intent match): bind only the selected tools.
- **Medium**: bind selected tools plus the clarification path (`ask_user` is already always-on).
- **Low**: **fall back to all enabled tools.** The selector must improve reliability, not become a bottleneck that blocks unusual prompts.

**e. Always-include.** Union the `always_include` set (`ask_user`) into the final bound set on every turn — regardless of selection or fallback. Without this, HITL routing (`is_ask_user_tool_call` → `hitl` node) breaks.

**Edge case — zero survivors after hard filters** (e.g. Todoist disabled): bind only the `always_include` set; the model answers or asks for clarification.

**Multi-turn note.** Selection is computed per agent turn from the latest user request. Because dependency expansion binds lookup + mutation together up front, a request like "mark buy groceries as done" already has both `get_tasks` and `complete_task` available across the loop's turns — the model can look up on turn 1 and complete on turn 2 without re-selection surprises.

## 8. Multi-App Extension Guide

Adding a new app is registration only — no selector changes:

1. Define the app's tool schemas + executable wrappers under `tools/<app>/` (the `calendar/`, `gmail/`, `notion/` placeholders already exist).
2. Register a `ToolSpec` per tool with its `app`, `intents`, `aliases`, `patterns`, `mutates`, and `dependencies`.
3. Add the app's intent ids to the taxonomy (§9).

The hard filters, matcher, dependency expansion, confidence gate, and tracing all operate on `ToolSpec` records generically, so they pick up the new app automatically.

---

## 9. Intent Taxonomy (per app)

Intents are namespaced per app (`task.create`, `calendar.block`, `mail.send`, …) so taxonomies don't collide as apps are added. Todoist is the concrete worked example:

| Intent | Tools selected (after dependency expansion) |
|---|---|
| `task.create` | `add_todoist_task` |
| `task.read_active` | `get_tasks` |
| `task.read_completed` | `get_completed_todoist_tasks_by_completion_date` |
| `task.update` / reschedule / priority | `get_tasks` + `update_todoist_task` |
| `task.complete` | `get_tasks` + `complete_task` |
| `task.delete` | `get_tasks` + `delete_todoist_task` |

### Worked routing examples (from the draft, preserved)

- "show me my tasks" → `task.read_active` → `get_tasks`.
- "add submit tax form today at 5pm" → `task.create` → `add_todoist_task`.
- "add lunch with Feebee next week Wednesday at 12:30pm" → `task.create` → `add_todoist_task`.
- "what did I complete this week" → `task.read_completed` → `get_completed_todoist_tasks_by_completion_date`.
- "mark buy groceries today at 6pm as done" → `task.complete` → `get_tasks` + `complete_task`.
- "set my submit tax form task to high priority" → `task.update` → `get_tasks` + `update_todoist_task`.
- "reschedule lunch with Feebee from Wed 12:30 to Fri 1pm" → `task.update` → `get_tasks` + `update_todoist_task`.
- "delete the travel pillow packing task" → `task.delete` → `get_tasks` + `delete_todoist_task`.
- "add 8 packing tasks for my Korea trip: …" → `task.create` (bulk) → `add_todoist_task`; the orchestrator calls it once per task.
- "remind me to drink water every 2 hours starting tomorrow 9am" → `task.create` (recurring) → `add_todoist_task`; recurrence encoded in the Todoist due string.
- "add send Feebee off at 7pm p1 **and** mark study with Feebee as done" → multi-intent (`task.create` + `task.complete`) → union: `add_todoist_task` + `get_tasks` + `complete_task`.

## 10. Confidence and Fallback Rules

Signals that raise confidence:

- Clear create phrase: "add", "create", "remind me".
- Clear read phrase: "show", "what tasks", "due", "overdue", "inbox".
- Clear completed phrase: "what did I complete", "completed this week".
- Clear update phrase: "reschedule", "move", "change", "set priority", "edit".
- Clear completion phrase: "mark as done", "complete", "done".
- Clear deletion phrase: "delete", "remove".
- Time expressions matching Todoist due-date behaviour; priority expressions (p1–p4, "high priority").

Example selection reasons (surfaced in `SelectionResult.reasons`): *matched create phrase "add"*, *added dependency `get_tasks` because completion needs lookup*, *mutation mode enabled*, *fell back to all enabled tools — no confident intent match*.

Behaviour: **high** → selected only; **medium** → selected + clarification; **low** → all enabled tools. Keep *intent* confidence separate from general *app* confidence so a request that clearly belongs to Todoist but has a fuzzy action doesn't either over-narrow or over-broaden.

## 11. Tracing and Observability

Log the decision **before** binding, reusing `TracePrinter.event(...)` and the existing `noun.verb` event-name convention (`tool.*`, `graph.*`, `agent.*`):

- `tools.select.start` — query length, candidate count, active strategies, `allow_mutations`.
- `tools.select.filtered` — rejected tools + reasons (hard filters).
- `tools.select.matched` — detected intents, per-tool scores.
- `tools.select.expanded` — dependency tools added.
- `tools.select.result` — final selected names, `fallback_used`, bound tool count.

These answer the questions that otherwise look like model-reasoning bugs: *Why didn't the model have the delete tool? Why were mutation tools removed? Why did it fall back to all tools? Why was `get_tasks` added to a completion request?* Without selection traces, you can't tell whether the model chose the wrong tool or never received the right one.

## 12. Failure Modes (refined)

- **Selector too strict** — required tool filtered out. *Mitigation:* low-confidence fallback, automatic dependency expansion, richer aliases/patterns, no hard-filtering on weak semantic guesses.
- **Selector too loose** — almost every request still gets many tools. *Mitigation:* separate intent vs app confidence, require clear matches for high-confidence routing, tighten broad patterns, log tool count per request.
- **Ambiguous short prompts** ("add this later") — likely Todoist create but missing content/time. *Mitigation:* select the create tool; `ask_user` is already bound for the missing detail; don't expose unrelated tools unless confidence is low.
- **Multi-intent prompts** — return the union of required tools; preserve dependency expansion.
- **Bulk prompts** — one intent, many calls; select the create tool and let the orchestrator decompose.
- **Existing-task mutation without ID** — always include `get_tasks` before update/complete/delete (dependency expansion).

## 13. Success Criteria

- Obvious create requests bind only `add_todoist_task` (+ always-on `ask_user`).
- Obvious read requests bind only `get_tasks`.
- Complete/update/delete requests bind the lookup tool plus the mutating tool.
- Completed-task queries bind the completed-task tool.
- Bulk create binds the create tool; multi-intent binds the union.
- Mutating tools are not bound when `ALLOW_MUTATIONS` is off (and stay enforced at the dispatcher).
- `ask_user` is bound on every turn; HITL still works.
- Low-confidence queries fall back to all enabled tools.
- Selection decisions are logged and inspectable.
- Average tools bound per request, wrong-tool calls, and prompt tokens all decrease.
- Adding a new app (calendar/gmail/notion) requires registry registration only — no selector changes.

## 14. Recommended Implementation Priority

- **P0 — Tool Registry.** App-agnostic `ToolSpec` registry as the single source of truth; `get_todoist_tools()` derives from it (keeps `service.py` / tests green).
- **P1 — Hard filters.** Registry-driven eligibility: enabled, healthy, auth, mutation mode, permissions (static defaults where infra is absent). Immediate safety + hygiene.
- **P2 — Deterministic matcher.** Alias/regex/intent matching behind the `MatchStrategy` interface; the create/read/update/complete/delete/completed intents.
- **P3 — Dependency expansion.** Auto-include lookup tools before mutations.
- **P4 — Multi-intent + confidence/fallback.** Union of intents; high/medium/low gate with all-enabled fallback.
- **Later — BM25 / semantic strategy** (drop-in via `MatchStrategy`) and **real health/auth checks** (wire the static registry fields to live state; ties into [§3.4](03-agent-intelligence.md)).

The first shippable version is deterministic, single-app (Todoist), and modular by construction — the BM25 and multi-app seams exist from P0 even though they're not exercised yet.

## 15. Open Questions

- **BM25 corpus & integration point.** What text feeds the lexical index (tool description + aliases + intent labels?), and where is it rebuilt when the registry changes? The `MatchStrategy` interface fixes the *call site*; the corpus design is open.
- **Health/auth wiring.** The `enabled`/`healthy`/`requires_auth` fields are static placeholders until [§3.4](03-agent-intelligence.md) lands runtime health checks and per-integration auth state. Decide whether the selector reads those live or caches them per run.
- **Selection caching across turns.** Whether to compute `SelectionResult` once per user request and reuse across the agent loop's turns, or recompute each turn. (Dependency expansion makes recomputation safe either way.)
- **Strategy composition policy.** When multiple strategies are active, confirm max-score merge is the right combiner vs. weighted blend.
