# Full Telegram-to-Agent E2E Testing Pipeline

## Summary

There is no reliable full-suite E2E pipeline today.

Current coverage is strong at the component level, but the closest E2E pieces are incomplete:

- The webhook integration test mocks the message processor and Telegram reply.
- The live webhook test verifies a Todoist side effect but races background processing and never verifies the outgoing Telegram response.
- `scripts/run_telegram_e2e.sh` is broken because its `scripts/simulate_telegram_update.ts` dependency was deleted.
- Webhook HTTP 200 only means “accepted”; processing happens asynchronously, so it is not a completion signal.
- Voice currently has unit coverage but no test that moves real audio bytes through Telegram file lookup, download, transcription, the agent, and the final reply.

Build three test tiers:

1. `test:e2e`: fast, deterministic application E2E with real TypeScript pipeline and fake external services.
2. `test:e2e:stack`: real TypeScript server, Python FastAPI graph, and isolated database, with deterministic model/tool adapters.
3. `test:e2e:live`: opt-in real Groq/model/integration and genuine Telegram-network acceptance tests.

## Implementation Changes

### 1. Make the production pipeline testable without bypassing it

- Extract the composition currently performed as import-time side effects in `src/app.ts` into a side-effect-free `createJarvisApplication(options)` factory.
- The factory must construct the same authorization, Telegraf, handlers, processors, conversation gate, pending store, Whisper, and LangGraph client used in production.
- Keep all production defaults unchanged while allowing tests to inject only external boundaries:
  - Telegram Bot API root and file-download root.
  - Groq/OpenAI client or Groq base URL.
  - LangGraph base URL/client.
  - Authorization, pending-state, and conversation-gate stores.
  - Optional processing observer used by the test harness.
- Add an internal processing observer keyed by `tg_update_<update_id>` that reports `started`, `completed`, `denied`, or `failed`. The production observer is a no-op.
- Preserve the immediate webhook 200 response. E2E tests must separately assert:
  1. Webhook acceptance.
  2. Handler completion.
  3. A captured final Telegram reply.
- Make `FileService` build file URLs from configurable Telegram roots instead of hard-coding `api.telegram.org`.
- Make `WhisperService` accept an injected client/base URL so the deterministic suite can validate real multipart audio requests against a local fake Groq server.

### 2. Add deterministic fake external services

Create an E2E harness that starts isolated services on ephemeral ports:

- Fake Telegram Bot API:
  - Implement `getMe`, `getFile`, file download, `sendMessage`, rich-message calls, edit/delete, callback answers, and command/webhook setup as required.
  - Record ordered outbound calls by chat ID and test correlation ID.
  - Allow scripted failures for formatting fallback, file-download failure, and Telegram API errors.
- Fake Groq transcription endpoint:
  - Accept the real multipart upload generated by `WhisperService`.
  - Validate model, filename, content type, and non-empty audio bytes.
  - Return the transcript declared in the fixture manifest.
  - Support scripted 429, timeout, malformed response, and permanent failure behavior.
- Fake LangGraph HTTP service for the fast tier:
  - Implement `/invoke`, `/invoke/stream`, `/resume`, `/resume/stream`, and health routes using the real TS/Python contract.
  - Assert `source=telegram`, Telegram identity, `request_id`, thread ID, and exact prompt/transcript.
  - Script completed, clarify, confirm, failed, malformed-stream, timeout, and retry scenarios.
- Give every scenario unique update, message, chat, user, thread, and side-effect markers.
- Wait on explicit observer and captured outbound events with bounded timeouts; never poll application logs as the success oracle.

### 3. Add a real Python-stack deterministic tier

- Refactor the Python FastAPI app factory to accept runtime dependencies for tests while retaining production defaults.
- Run the actual FastAPI routes, streaming protocol, graph assembly, routing, HITL behavior, tool dispatch, and response serialization.
- Inject a scripted model and deterministic tool adapters at the model/provider boundary rather than replacing graph nodes.
- Start an isolated local Postgres database/schema, apply migrations, provision test Telegram identities, and clean it after the suite.
- Exercise TS webhook → Telegraf → processor → HTTP stream → real Python graph → TS formatter → fake Telegram reply.
- Add database-backed restart cases for pending clarifications, thread ownership, and idempotency.
- Capture Python diagnostics through `run_logging.py`; capture TypeScript diagnostics through the existing async logger. Flush both before log assertions or shutdown.

### 4. Replace the broken simulator with a scenario runner

Add a CLI capable of running one case or a manifest:

- Inputs:
  - `--text "..."`.
  - `--voice <path>`.
  - `--audio <path>`.
  - `--document <path>`.
  - `--scenario <json-file>`.
  - User/chat selectors, timeout, deterministic update ID, and target tier.
- For local audio cases, register the file with the fake Telegram server and generate a Telegram-shaped `voice`, `audio`, or `document` update.
- Print a concise pass/fail summary containing acceptance, processing status, transcription, final reply, duration, and correlation ID.
- Exit nonzero on rejection, background failure, missing reply, unexpected side effect, or timeout.
- Support JSON and JUnit output for CI.
- Replace stale package scripts/tests rather than restoring the old text-only, acceptance-only behavior.

Suggested commands:

- `npm run test:e2e` — deterministic fast suite.
- `npm run test:e2e:stack` — real Python graph and isolated database.
- `npm run test:e2e:live:voice` — real Groq transcription.
- `npm run test:e2e:live:services` — real model and reversible integrations.
- `npm run test:e2e:telegram` — dedicated Telegram user acceptance.
- `npm run test:full` — build, TS unit/integration, Python tests, contracts, and deterministic E2E.

## E2E Test Matrix

### Text and transport

- Valid text webhook:
  - HTTP 200 acceptance.
  - Authorization succeeds.
  - Correct identity and `tg_update_<id>` reach Python.
  - Progress messages are emitted and cleaned up.
  - Final Telegram reply contains the scripted result.
- Wrong webhook secret returns 401 and triggers no processing.
- Unauthorized user receives the private-bot response and never calls the agent.
- Empty, unsupported, and malformed updates return the expected safe response without crashing.
- Rich-message success, rich-message failure with Markdown fallback, Markdown escaping, tables, and long-response splitting.
- Agent stream progress followed by a final event.
- Streaming endpoint unavailable before data: standard `/invoke` fallback succeeds.
- Mid-stream disconnect, malformed response, 4xx, 5xx, and timeout produce a user-safe terminal reply and a failed observer state.

### Conversation behavior

- Clarification interrupt followed by a text reply calls `/resume/stream` with the original thread.
- Clarification can be answered with a voice message.
- Confirmation renders Approve/Decline buttons; approve resumes once, decline does not mutate.
- `/new` abandons pending clarification and begins a fresh thread.
- `/cancel` clears pending state and prevents subsequent stale resume.
- Reply-to-message context is included only when appropriate.
- Two users and two chats maintain separate gates, pending state, threads, and credentials.
- Rapid messages verify serialization/buffering behavior.
- Duplicate Telegram update IDs produce one agent execution, one mutation, and one terminal reply.
- Process restart preserves or expires pending clarification according to the database-backed policy.

### Voice, audio, and documents

For each happy-path case, assert:

`Telegram update → getFile → fixture download → multipart transcription → transcript reply → exact transcript sent to agent → final Telegram reply`

Cases:

- Native Telegram OGG/Opus `voice`.
- MP3 or M4A `audio`.
- WAV/MP3 sent as an audio `document`.
- Audio used as clarification input.
- Silence/no speech: “No speech detected” and no agent request.
- Corrupt audio and invalid container.
- Oversized input generated during the test.
- Telegram `getFile` failure and file-CDN download failure.
- Groq 429 with bounded retry, timeout, malformed response, and permanent failure.
- Direct-format transcription failure followed by real FFmpeg conversion fallback.
- Transcription-message send failure still permits agent execution and the final reply.
- Concurrent voice and text updates respect the conversation gate.

### Live-provider tests

- Run several short personal voice recordings through real Groq.
- Compare normalized key phrases or word-error-rate thresholds rather than punctuation-exact transcripts.
- Run read-only prompts through the real model and graph.
- Run one reversible mutation per configured integration using a unique marker.
- Poll the external side effect with a timeout and always clean it in `finally`.
- Verify both the external side effect and the final captured Telegram response.
- Keep live tests environment-gated and outside the default pull-request suite.

### Genuine Telegram-network acceptance

- Use a dedicated Telegram test user through MTProto/Telethon; Bot API cannot send inbound messages as a human user.
- Store API credentials and the encrypted session only in local/CI secrets.
- Restrict the bot and test user to a dedicated private test chat.
- Send correlated text and voice messages, then wait for the bot’s transcription/final reply.
- Test one text happy path, one native Telegram voice note, and one clarification/resume flow.
- Run manually or on a protected schedule, not in default CI, because Telegram networking and rate limits are nondeterministic.

## Audio Fixtures and Artifacts

- Add `tests/fixtures/audio/manifest.json` containing:
  - Fixture path and Telegram envelope type.
  - MIME type and extension.
  - Expected deterministic transcript.
  - Expected live key phrases/tolerance.
  - Expected agent scenario.
- Commit short synthetic/non-sensitive fixtures for CI, including native OGG/Opus.
- Store personal recordings under `tests/fixtures/audio/personal/` and gitignore that directory by default because voice recordings are biometric data.
- Generate silence, oversized, and corrupt boundary fixtures during the test instead of committing large binaries.
- On failure, retain sanitized fake-service request transcripts, correlation IDs, timing, and application logs under a per-run artifact directory.
- Do not extend the existing synchronous test logger pattern. New TypeScript diagnostics must use `src/utils/logger.ts`; Python diagnostics must use `run_logging.py`.

## Delivery Order and Acceptance

1. Refactor composition and external-service configuration without changing production behavior.
2. Add fake Telegram, Groq, and LangGraph services plus explicit completion observation.
3. Implement the core text and OGG voice happy paths.
4. Add HITL, idempotency, concurrency, error, and audio-format cases.
5. Add the actual Python graph/database stack tier.
6. Replace the broken simulator and add `test:full`.
7. Add opt-in live Groq/integration tests.
8. Add dedicated-user Telegram acceptance after credentials are provisioned.

The work is complete when one command can run the deterministic full suite from a clean checkout, each case proves both webhook receipt and final Telegram delivery, audio tests move actual bytes through the pipeline, failures are correlated and diagnosable, and all spawned services are terminated even after a failed test.

## Assumptions

- The default suite uses webhook-shaped inbound updates and a fake Telegram Bot API; real Telegram-network acceptance is a separate protected lane.
- The fast and stack suites are deterministic; real model, transcription, and integration calls are opt-in.
- Personal voice recordings remain gitignored, while synthetic audio fixtures are committed for CI.
- No production-only diagnostic endpoint is exposed; test completion observation is injected at the composition boundary.
- Existing user-owned worktree changes are unrelated and must remain untouched.
